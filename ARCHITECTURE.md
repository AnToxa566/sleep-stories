# Architecture

Decisions recorded on 2026-10-08, before any feature code exists. Library versions are pinned at install time; before writing setup code for any dependency, check its current documentation, because setup steps change between major versions.

Every decision below carries one sentence on what it buys and what it costs. A decision stated without its reason reads as arbitrary and gets undone, so keep the reasons when editing.

## 1. Purpose and scope

Sleep Stories plays a queue of short, AI-generated stories in Russian so a person can fall asleep to them. A story is usually one to three minutes long, never longer than about three. A typical night is two or three stories.

MVP scope:

- Accounts. Each person signs in and has their own profile (email and password, Google, Apple).
- Onboarding: choose a narrator voice, interests and story styles.
- A queue that is already filled when the app opens. The backend keeps adding stories while the person listens, so there are always unheard ones.
- Offline playback with background audio, from files downloaded in advance.
- At the end of the queue a gentle sound (waves) plays for about 20 seconds and fades out, and the screen shows a visual hint of what to do to continue. A touch anywhere on the screen during that time continues the night with more stories; no touch fades the audio out and stops. The screen stays on during the night and dims itself (section 7, "The screen during a night"). Decided by the owner on 2026-10-29, replacing the earlier plan to ask aloud "Вы спите?" and listen for a spoken answer (section 10).
- Reuse of stories already generated for other people (moved here from "Deferred" by the owner on 2026-10-30): the queue is filled first from ready stories that fit the person, and new generation starts only when they are not enough (section 6, "Queue top-up"). Only topics proposed by the system are reused, never one a person requested by typing it.
- A daily generation limit per person: at most 5 audio renders and 3 topic generations in a rolling 24 hours (section 6, "Queue top-up").
- A history of what was listened to.
- Ratings: a person can rate a story (`story_ratings`, one rating of -1 or 1 per user and story). Moved out of "Deferred" by the owner. Buys the rating data from day one, so the later recommendation algorithm has history to use; costs a rating control in the UI, and where in the app a person rates is not decided (section 11).
- Russian only. Dark UI only.

Story styles: «Факты» (facts), «Сказка» (fairy tale), «История» (historical story).

```
│  - player, queue     │ ◀──────────────────────── │  - user routes            │
│  - local STT / voice │                           │  - /internal/* routes     │
│    detection         │                           └──┬────────┬───────────┬───┘
└─────────┬────────────┘                              │        │           │
          │ sign-in only                              │ Prisma │           │ enqueue
          ▼                                           ▼        │           ▼
┌──────────────────────┐                  ┌────────────────────┐│   ┌───────────────┐
│  Supabase Auth       │                  │ Supabase Postgres  ││   │ Cloud Tasks   │
└──────────────────────┘                  └────────────────────┘│   └──────┬────────┘
                                                                │          │ HTTP + OIDC
          signed URL (short-lived)                              ▼          │ (retries, rate limit)
┌──────────────────────┐  upload  ┌────────────────────┐   ┌────────────┐  │
│  Supabase Storage    │ ◀─────── │ providers          │ ◀─┤ LLM / TTS  │ ◀┘
│  (private bucket)    │          │ (adapters in API)  │   └────────────┘
└──────────────────────┘          └────────────────────┘
        ▲
        └── mobile downloads audio with the signed URL, then plays the local file

Cloud Scheduler ──▶ API /internal/* (periodic queue top-up)
```

The mobile app talks to exactly two things: the API (with the user's JWT) and Supabase Auth (to sign in). It never reads tables, never holds a provider key, and downloads audio only through signed URLs that the API hands out.

## 3. Monorepo and module boundaries

Nx workspace, npm, TypeScript in strict mode.

| Path | Tag | May import |
|---|---|---|
| `apps/mobile` | `scope:mobile` | `scope:shared` |
| `apps/api` | `scope:api` | `scope:shared` |
| `packages/contracts` | `scope:shared` | nothing except `zod` |

- `packages/contracts` holds Zod schemas and the types inferred from them: request and response bodies, the structured output expected from the LLM, shared enums. It buys a single source of truth for both apps without code generation; it costs coupling of the two apps to the same schema version, which is fine inside one repository.
- `packages/contracts` stays framework-free (no React Native, no Nest, no Prisma). If it grows a framework import, the mobile app and the API can no longer share it.
- The module-boundary rule is not configured yet. When it is added (`@nx/enforce-module-boundaries` with the tags above), prove it by adding a forbidden import on purpose and confirming that lint fails, then remove it. A boundary rule that nothing tests is documentation, not enforcement.

Target layout (created when first needed, not before):

| What | Where |
|---|---|
| Screens, navigation, hooks, stores | `apps/mobile/src` |
| Nest modules, one per feature | `apps/api/src/app/<feature>` |
| Prisma schema and migrations | `apps/api/prisma` |
| Local Supabase stack configuration | `apps/api/supabase` |
| Generated Prisma client (git-ignored, never edited by hand) | `apps/api/src/generated/prisma` |
| LLM, TTS and storage adapters | `apps/api/src/app/providers` |

## 4. Backend

**NestJS on Cloud Run, built as a Docker image.** Buys scale-to-zero and a familiar modular framework with a validation pipeline; costs cold starts and the fact that CPU is throttled outside of a request (see Background jobs).

**Prisma with Supabase Postgres.** Prisma Migrate owns the schema, and Supabase is only the host. Buys one place where the schema is defined and a typed client; costs that Supabase's own `auth` schema is not managed by Prisma. Reference the auth user id as a plain uuid and do not create a foreign key into the `auth` schema. Connect through Supabase's connection pooler, because Cloud Run opens many short-lived connections. Set up on 2026-10-09 with Prisma 7.10.0, checked against its documentation:

- **Two connection strings.** `DATABASE_URL` is the transaction pooler (port 6543) and is used by the running API. `DIRECT_URL` is the session pooler (port 5432) and is used only by the Prisma CLI through `apps/api/prisma.config.ts` (Prisma 7 keeps the URL there, not in `schema.prisma`). Buys migrations and the shadow database on a connection type that supports them while the API uses the cheaper pooled one; costs two variables, and `prisma generate` also fails when `DIRECT_URL` is unset (see section 11). The session pooler is used instead of the direct `db.<ref>.supabase.co` host because that host is IPv6-only and not reachable from every network.
- **Driver adapter.** The API builds `PrismaClient` with `@prisma/adapter-pg` on `pg`, in one place (`PrismaService`). Buys the Prisma 7 query compiler without a native engine binary; costs two more dependencies. `connectionTimeoutMillis` is 10 seconds so a stuck connect fails instead of hanging a request. `?pgbouncer=true` is not used (the adapter ignores it) and `statementNameGenerator` is not set. Pool size is left at the `pg` default; see section 11.
- **TLS to the database (runtime).** The API verifies the pooler's certificate against Supabase's public root CA, pinned in the repository as a string in `apps/api/src/app/prisma/supabase-ca.ts` (CN=Supabase Root 2021 CA, expires 2031-04-26; source URL and SHA-256 fingerprint are in the file) and passed as `ssl: { ca }`. Buys encrypted and verified traffic without changing any trust store and without `rejectUnauthorized: false`; without the CA, `ssl: true` fails with `SELF_SIGNED_CERT_IN_CHAIN` and the default `pg` connection is plaintext. Costs a Supabase-specific constant that must be rotated by hand before 2031 or if Supabase changes its CA. `pg` merges parameters from the connection string over the options passed in code, so a `?sslmode=disable` in `DATABASE_URL` would silently turn TLS off; the Zod env schema therefore rejects any `ssl*` parameter (and `uselibpqcompat`) in `DATABASE_URL`, with a message that does not echo the value.
- **Generated client.** `prisma-client` generator, output `apps/api/src/generated/prisma`, `moduleFormat = "cjs"` because the API is CommonJS under webpack. The directory is git-ignored and rebuilt by the `prisma-generate` Nx target, which `build`, `lint`, `typecheck` and `test` of `api` depend on. Buys no generated code in review; costs that a fresh checkout must run generate (Nx does it).
- **`dotenv`** (dev dependency, owner-approved) is imported only by `prisma.config.ts`. Buys that the Prisma CLI reads `apps/api/.env` when `prisma` is run directly (under Nx the file is already injected into every `api` task); costs a second env loader next to `@nestjs/config`, in the dev dependencies only. The running API reads the same file through `@nestjs/config` (version 4, the last CommonJS line; version 12 is ESM-only while the API is CommonJS). One env file buys one place to look; costs that `.env` loading is done by two mechanisms.
- **Raw SQL in the first migration.** Row level security on every table (and on `_prisma_migrations`, guarded because the table does not exist in Prisma's shadow database), CHECK constraints, and the partial unique index on `generation_jobs.dedupe_key`. Prisma's schema language has no syntax for RLS or CHECK constraints. Prisma 7.10 has a `partialIndexes` preview feature that could describe the partial index, but it is not enabled: a preview feature can change between releases, and one raw statement next to the others is simple. Buys database-enforced invariants and no preview dependency; costs that they are not visible in `schema.prisma`, so the schema carries comments pointing at them.
- **Local development (decided 2026-10-29).** The default database for development is the full Supabase stack run by the Supabase CLI in Docker (`npx nx supabase-start api`, configuration in `apps/api/supabase/config.toml`), not the cloud project. Reason: a free-tier project pauses after a week of inactivity (section 11, item 10), work has to be possible offline, and a disposable database can be reset or broken without care. Prisma still owns the schema: `[db.migrations]` and `[db.seed]` are disabled in `config.toml`, and the schema is applied with `prisma migrate deploy`. Realtime, edge runtime and analytics are switched off; Auth, the API gateway, Studio, the mail catcher and, since 2026-10-30, Storage (one private bucket `audio`, see section 5) are on. Email confirmation is off locally; it is a pre-launch checklist item in SECURITY.md (confirmation on in the cloud project). In `apps/api/.env` the cloud connection lines are commented out in place with the prefix `# cloud: ` and the local ones are active; `apps/api/.env.example` uses the same convention.
  - **The CLI** is the npm package `supabase`, a root dev dependency (owner-approved on 2026-10-29) pinned to 2.121.0, the newest release at least 14 days old (2.122.0 was six days old); the version is in the lockfile. Homebrew was not used because formula installs fail on the owner's Mac: its Command Line Tools are too old for macOS 27 (observed on 2026-10-29). The `jose` entry that the CLI brings into the lockfile is its own transitive dependency; the API pins and declares its own copy (`jose` 6.2.12, used for JWT verification, section 8).
  - **Buys** no paused project, offline work and a database that can be thrown away.
  - **Costs:** Docker memory and a first image download. As a root dev dependency, `supabase` and its platform binary are installed by every full `npm ci`, including EAS builds (they copy the root `package.json` and lockfile); this is not fixed here. `minimum_password_length` is 8 instead of the CLI default 6, to match the design's sign-up rule ("Не короче 8 символов"). A local database that can drift from the cloud one (the cloud database is migrated only on purpose). The local database is not pooled (`[db.pooler] enabled = false`), so local runs never exercise transaction-pooler behaviour; the cloud runtime does. The CLI has telemetry enabled by default (`npx supabase telemetry status` says so) and checks for updates; the setting was left unchanged and the owner can turn it off.
  - **LAN exposure.** The CLI publishes 54321 (the API gateway; its default service-role key is public and bypasses RLS), 54322 (Postgres, public default password `postgres`), 54323 (Studio, an unauthenticated SQL and admin interface) and 54324 (the mail catcher) on all network interfaces (checked with `docker ps`). Use the stack only on trusted networks, never on public Wi-Fi, and stop it after work (`npx nx supabase-stop api`). Recorded in the SECURITY.md threat model. The local keys are the CLI's public defaults and are not secrets; the real secrets remain only in the cloud `.env` lines.
  - **Connected (2026-10-29).** `DATABASE_TLS` is read at boot (`apps/api/src/app/prisma/database-tls.ts`, with the environment schema). Plaintext is allowed only when `DATABASE_TLS=disabled-local-only` and the database host is loopback and the process is neither on Cloud Run nor in production; in every other case the API refuses to start. Verified by unit tests and by booting against the local stack. `SUPABASE_URL` is read too: the API takes the token issuer and the key set from it (section 8). The local stack stamps tokens with `iss=http://127.0.0.1:54321/auth/v1` whatever address the client used, so the API keeps the loopback `SUPABASE_URL` while the phone reaches Auth and the API through the Mac's LAN address.
  - **Open check.** The local Postgres major version (17, the CLI default in `[db] major_version`) was not compared with the cloud project. Check it with `SHOW server_version` in the cloud project and align `[db] major_version`.

**All data goes through the API, and tables have RLS enabled with no policies.** Buys exactly one authorization layer, written in TypeScript; costs that the mobile app cannot query Supabase directly or use realtime subscriptions.

**Validation and configuration.** Zod everywhere (`nestjs-zod` in the API). `@nestjs/config` with a Zod schema, so a missing secret crashes the process at boot instead of failing later at the first request.

**Hardening and operations.** `helmet`, `@nestjs/throttler`, `nestjs-pino` (structured logs go to Cloud Logging), `@nestjs/swagger`. Secrets live in Google Secret Manager. CI/CD is GitHub Actions building the image and deploying to Cloud Run with Workload Identity, so there are no long-lived keys in the repository.

**Background jobs: Cloud Tasks, with Cloud Scheduler for periodic triggers.**
Generating one story takes tens of seconds: an LLM call, a TTS call and an upload. Cloud Run limits CPU outside of an active request and can stop an idle container, so doing this "after the response" silently loses work. Cloud Tasks stores the job durably and calls an API endpoint, which keeps a request open for the duration of the work, retries failures with backoff, and caps concurrency so provider limits and costs are protected. It needs no Redis. It costs coupling to GCP, internal endpoints that must authenticate the caller, and an open question about local development (see Known open problems). The simpler alternative that was considered, a jobs table polled by Cloud Scheduler, was passed over because retries and concurrency control would have to be hand-written.

**Provider adapters.**
- `LlmProvider` wraps `@anthropic-ai/sdk` (the official SDK, owner's choice of 2026-10-30) and uses Haiku for both topics and stories (owner, 2026-10-30). The model id is the env value `ANTHROPIC_MODEL`, default `claude-haiku-5-5`, confirmed by a real call in the paid smoke test (owner, 2026-10-30). Topic lists and story metadata come back as structured JSON validated with Zod.
- `TtsProvider` wraps the speech provider, which is ElevenLabs (chosen by the owner on 2026-10-30 after testing it in Russian). The owner chose the official ElevenLabs SDK on 2026-10-30. The model id is the env value `ELEVENLABS_MODEL`, default `eleven_v4`; the package types do not confirm `eleven_v4` for text-to-speech, but the paid smoke test ran with it and passed (owner, 2026-10-30). Text-to-speech through the API needs a paid ElevenLabs plan: on the free plan the smoke test's request failed (owner's account page, 2026-10-30; the status code was not recorded) and passed after the owner bought a paid plan. The plan is a fixed monthly cost besides the per-character use (relevant to section 11, item 8). The SDK is imported only inside this adapter and the key lives only on the server. The four narrator voices are catalogued in the `voices` table (provider `elevenlabs`, its voice id in `provider_voice_id`); the voice ids are identifiers, not secrets, and are never sent to the app.
- Storage is Supabase Storage in a private bucket.
- **SDKs installed (2026-10-30), exact pins:** `@anthropic-ai/sdk` 1.3.0 (published 2026-10-23, under 14 days old at install; accepted by the owner), `@elevenlabs/elevenlabs-js` 2.73.0, `music-metadata` 12.2.1. Each is imported in one file only: the two adapters (`anthropic-llm.provider.ts`, `elevenlabs-tts.provider.ts`) and `generation/audio-duration.ts`; no lint rule enforces this yet, a grep does.
- **`maxRetries: 0` in both adapters.** Cloud Tasks owns retries; hidden SDK retries would double the spend without anyone counting them. Each adapter sets an explicit timeout.
- **Error text is never forwarded.** An SDK error message can embed a response body that echoes the request, so the adapters throw `LlmProviderError` / `TtsProviderError` with a fixed message and read only the numeric status to set `retryable` (408, 429 and 5xx are retryable).
- **Structured output is re-checked.** The Anthropic SDK strips length keywords (`minLength`, `maxItems` and the like) from the JSON schema it sends, so the model is not held to them; Zod from `packages/contracts` re-checks every constraint on the reply.
- **`music-metadata` is ESM-only,** like `jose`: webpack keeps it external and Node 24 `require()`s it (`node -e "require('music-metadata')"` works). Jest cannot load it by default: `jest.config.cts` and `jest.integration.config.cts` add it and its ESM-only dependencies to the `transformIgnorePatterns` exception and map the bare name to its Node entry file (Jest picks the `types` condition otherwise). The list is revisited when it is upgraded.
- The lockfile moved the transitive `strtok3` from 10.3.5 to 10.6.3 (it is also used by `@nestjs/common`'s `file-type`).

Buys: replaceable vendors and one place where keys and spend are controlled. Costs: one small interface per provider.

**One story, one request.** A story is generated whole: one LLM call, one TTS request, one audio file in MP3 or AAC. Stories are short enough that nothing needs splitting, so there is no chunking and no ffmpeg. The audio duration is read from the file with `music-metadata`. The one thing to verify on the chosen TTS provider is its per-request text limit (a three-minute Russian story is roughly 2,500 to 3,500 characters). If a provider's limit is lower than that, revisit this decision with the owner instead of adding chunking quietly.

**Storage: Supabase Storage rather than Google Cloud Storage.** Buys one vendor next to the database and auth, a built-in CDN, and a one-call signed URL; costs that files live on a different cloud than the API. Compared on 2026-10-08, and worth rechecking before relying on it:

| | Supabase | Google Cloud Storage (EU regional) |
|---|---|---|
| Storage | Free 1 GB; Pro ($25/month) includes 100 GB, then about $0.0213/GB | about $0.020/GiB-month |
| Egress | Free 5 GB; Pro includes 250 GB, then $0.03/GB cached or $0.09/GB uncached | $0.12/GiB (first 10 TiB per month) |
| Max file | Free 50 MB; Pro 500 GB | no practical limit |
| Catch | Free projects are paused after a week of inactivity | pay from the first byte; free tier covers US regions only |

At a few users either option costs almost nothing. The database stores only the object path, never a URL, so moving to GCS later is a contained change.

Sources: [Supabase pricing](https://supabase.com/pricing.md), [Supabase Storage file limits](https://supabase.com/docs/guides/storage/uploads/file-limits), [Cloud Storage pricing](https://cloud.google.com/storage/pricing).

## 5. Data model

Decided and implemented in the first migration (`apps/api/prisma/migrations`, 2026-10-09). Do not add entities beyond this list without asking.

Naming: Prisma models are PascalCase singular with camelCase fields; tables are snake_case plural (`@@map`), columns are snake_case (`@map`), enum types and their values are snake_case. Surrogate primary keys are `uuid` with a database default of `gen_random_uuid()`; `users.id` comes from Supabase Auth and has no default, and composite primary keys need none. Timestamps are `timestamptz(3)`. `created_at` and `updated_at` default to `now()` (and Prisma maintains `updated_at`); `listens.listened_at`, `user_topics.dismissed_at` and the `started_at` and `finished_at` columns of `generation_jobs` have no default, because their values come from an event (the client's listen report, a dismissal, a job starting or finishing). Buys one predictable mapping and no surprises in SQL; costs the `@map` noise in the schema file.

| Group | Table | Purpose |
|---|---|---|
| Reference | `voices` | Narrator voices: slug, name, description, TTS provider and its voice id, object paths of the sample audio and of the pre-rendered «Вы спите?» prompt, sort order, active flag |
| Reference | `interests` | Interests offered in onboarding: slug, title, sort order, active flag |
| Users | `users` | One row per person. `id` is the Supabase auth user id (plain uuid, no default, no foreign key into `auth`). The cascade anchor for everything per-user |
| Per-user | `user_preferences` | Chosen voice and story styles (`story_style[]`, at least one). One row per user, created when onboarding finishes |
| Per-user | `user_interests` | Chosen interests, primary key (user, interest) |
| Per-user | `user_custom_interests` | Free-text interests a person typed, not blank |
| Content | `topics` | An idea for a story: title, style, optional interest. Not tied to one user |
| Content | `stories` | The finished text for a topic (one story per topic): text, character count, LLM model, prompt version. Created only when complete. No owner column |
| Content | `story_audio` | One audio file per (story, voice): object path, duration, byte size, MIME type, TTS provider |
| Per-user | `user_topics` | Topics offered to or requested by a person (`proposed` or `requested`), with `dismissed_at` when they said no |
| Per-user | `queue_items` | The person's queue: a topic and a position |
| Per-user | `listens` | One row per listening: story, voice, seconds listened, when |
| Per-user | `story_ratings` | One rating per user and story: `-1` or `1` |
| System | `generation_jobs` | One row per generation attempt chain: kind (`suggest_topics`, `write_story`, `render_audio`), payload, dedupe key, requesting user, status, attempt count, last error |

Rules that follow from the reasoning:

- **Content is separate from per-user state.** `topics`, `stories` and `story_audio` have no owner, so a story generated for one person can be offered to another with no migration (the reuse of section 6, "Queue top-up", decided on 2026-10-30). Everything per-user lives in the per-user tables above. Buys that reuse for free; costs a join to get "this person's story". A topic is eligible for reuse only if no `user_topics` row for it has the reason `requested`: text a person typed is never shown to anyone else (SECURITY.md, rule 10). No new column; the rule is a query condition.
- **`users` is the cascade anchor.** Every per-user table references it with `ON DELETE CASCADE`, so removing a person is one delete. `generation_jobs.requested_by_user_id` is `ON DELETE SET NULL` instead, so the cost history of generation survives the person (it costs a nullable column). Every reference to content and to reference data is `RESTRICT`, so shared content cannot disappear because of one deletion. The foreign key columns on the RESTRICT side (`listens.story_id`, `listens.voice_id`, `story_ratings.story_id`, `queue_items.topic_id`, `user_topics.topic_id`, `user_interests.interest_id`, `user_preferences.voice_id`, `story_audio.voice_id`) have no indexes of their own. That is a known cost: deleting a referenced row would scan those tables. Revisit it if deleting content is ever designed. Wiring the deletion of the Supabase auth user to the `users` row is not done yet.
- **The queue references topics, not stories.** A topic can be queued before its story exists, and the generation pipeline creates no queue row (section 6); the one thing it does to the queue is to delete the items that can no longer become ready when a job fails for good (section 11, item 13). Costs a join through `topics` to reach the audio. `queue_items` has a unique (user, topic) and an index on (user, position), and deliberately no unique on position: reordering rewrites positions inside one transaction without tripping over a transient duplicate.
- **Voice is per audio file.** `story_audio` is unique on (story, voice), so a story's text is written once and rendered per voice. Buys changing a voice without rewriting text; costs more audio rows and storage.
- **The listen outcome is derived, never stored.** `listens` records `listened_sec`; finished or skipped is computed from it and the audio duration. Buys that the threshold for "finished" can change without a data fix; costs a computation wherever the outcome is read. `listens.listened_at` has no database default because the value comes from the client event, and the index is (user, `listened_at` descending) for the history screen.
- **User intent and system health are separate axes.** What the person chose lives in the per-user tables. Whether the system managed to produce a story (`pending`, `running`, `succeeded`, `failed`) lives in `generation_jobs`. They are never merged into one enum, because recovering from a failure must not lose what the person chose.
- **At most one active job per dedupe key.** A partial unique index on `generation_jobs.dedupe_key` where the status is `pending` or `running` makes a duplicate request fail in the database, while a finished job and a new one may share a key. Buys idempotent enqueueing without locks; costs raw SQL outside Prisma's schema.
- **A story row exists only when complete.** A `stories` row holds finished text; its audio is a separate `story_audio` row per voice, created later. There are no half-filled stories, so no nullable text or audio columns that apply to only one lifecycle stage.
- **Ratings are in the MVP.** The data is recorded from day one (a rating per user and story, `-1` or `1`) together with listens. The algorithm that uses them is deferred; the data is not.
- **Paths, not URLs.** `story_audio.storage_path` (unique) and the voice audio columns hold storage object paths. Signed URLs are created per request and never stored.
- **Storage layout (decided 2026-10-30).** One private bucket, `audio` (config `AUDIO_BUCKET`, default `audio`; locally declared by `[storage.buckets.audio]` in `config.toml`, `public = false`; `supabase start` does not create it, run `npx supabase seed buckets` in `apps/api` once per fresh stack, checked 2026-10-30). Voice samples live at `voices/<slug>/sample.mp3`; story audio will join under `stories/`. The database stores the path relative to the bucket, so the bucket name is configuration, not data. `GET /voices` signs all active samples in one batched `createSignedUrls` call (a fixed number of round trips; one bad path fails the whole request with a 5xx, because a voice row without a playable sample is worse than a retry) with a 10-minute TTL (long enough for a slow voice step, short enough that a leaked URL dies soon) and returns them as `sampleUrl`; `sampleAudioPath` never leaves the server. The service-role client lives only in `apps/api/src/app/providers/storage` (no lint rule enforces this yet). The signed URL's host comes from `SUPABASE_URL` as the API sees it, so a phone can reach it only if that URL is reachable from the phone. The local stack signs with `127.0.0.1`, which a phone cannot reach, so an optional `STORAGE_PUBLIC_URL` (an origin such as `http://192.168.1.20:54321`) makes `StorageService` replace protocol, host and port of every signed URL (WHATWG `URL`; path and query are kept, because the token is bound to the object path, not the host; a URL that does not parse is a signing failure). It buys a playable sample on a real phone without touching the stack; it costs a dev-only knob, which `validateEnv` refuses on Cloud Run and when `NODE_ENV` is `production` (the same pattern as `DATABASE_TLS=disabled-local-only`) and which stays unset in production.
- **`generation_jobs.payload` is parsed, not trusted.** It crosses a boundary (SECURITY.md rule 5), so it is parsed by a Zod schema keyed on `kind`, with the schemas in `packages/contracts`. That package does not exist yet; this is a task for later.
- **Row level security is on for every table, with no policies,** including Prisma's `_prisma_migrations`. CHECK constraints enforce what the application also validates: at least one style, a non-blank custom interest, positive character count, duration and byte size, non-negative listened seconds, rating in (-1, 1).

## 6. Generation pipeline

The work is split into jobs of three kinds (`job_kind`). Each job is one `generation_jobs` row and one Cloud Task.

1. **Trigger.** After onboarding, when a person's queue has two items or fewer, on a Cloud Scheduler top-up, or on an explicit user request, the API runs the queue top-up (below), which creates `generation_jobs` rows and enqueues one Cloud Task per job. Queueing goes through one small interface with two implementations: Cloud Tasks, and a local one for development (see section 11, item 7).
2. **Dispatch.** Cloud Tasks calls an `/internal/*` endpoint with a Google OIDC token. The endpoint verifies the token before doing anything. Queue settings cap concurrent dispatches and rate.
3. **Idempotency and the claim.** Before any work the executor claims the job in one SQL statement: a `pending` job, or a `running` job whose lease (10 minutes) has run out, becomes `running`, `attempts` goes up by one, and the statement returns the row only when `attempts` is still below the limit of the kind. Two overlapping deliveries of one task cannot both claim it: the second finds a live lease and is answered 503, so the queue tries again later. A job that already succeeded or failed returns 200 without doing work, which protects against retries that arrive one after another. Each job kind marks the job `succeeded` in the same database transaction that creates its rows (step 4), through `markSucceeded(tx)`, which is conditioned on `status = 'running'` and on the claim's `attempts` value (a fence): a slow run whose lease was taken over cannot mark success, and its transaction rolls back with its rows. Storage objects can still be orphaned (section 11, item 18). See "How jobs run" below.
4. **The job kinds.**
   - `suggest_topics` creates topics, and the `user_topics` rows that record them as offered. The topics and `user_topics` rows are created in one transaction with marking the job `succeeded`.
   - `write_story` writes the story only, with no audio file yet. `LlmProvider` returns the text and metadata as structured output, validated with Zod, and the length is checked against the TTS limit. The `stories` row (text complete) is created in one transaction with marking the job `succeeded`.
   - `render_audio` creates the audio itself. It makes the TTS request through `TtsProvider`, reads the duration from the returned file, saves the file to private storage, and saves the `story_audio` row to the database in one transaction with marking the job `succeeded`.
5. **How this keeps "a story is generated whole".** One LLM call, in `write_story`. One TTS request per story and voice, in `render_audio`, returning one audio file. No chunking, no ffmpeg. Splitting the work into jobs changes who runs each step, not how many calls a story takes.
6. **Readiness.** A queue item is ready when a `story_audio` row exists for its topic's story in the person's voice. The pipeline creates no queue row; the queue references topics (section 5) and is filled by the top-up and managed by the user-facing API. The one exception is a final failure: in the transaction that marks the job `failed`, the runner deletes the queue items that wait for that result (section 11, item 13), so a stuck item never blocks the top-up.
7. **Chaining (decided 2026-10-30).** `render_audio` follows a successful `write_story`, in the voice of the person who requested it. The `write_story` handler inserts the `render_audio` row (payload: story id and voice id) in the same transaction that marks itself `succeeded`, and enqueues its task after the commit. This is a requirement for cycle 3b, not a preference: the limit counts a pending or running `write_story` and a pending or running `render_audio` as one render slot each, so the row must appear in exactly the transaction that ends the write; earlier (or in a separate transaction before) the slot is counted twice, later it is counted zero times. If that enqueue fails, the row stays `pending` and is picked up by the sweep of stuck jobs (section 11, item 13). The `dedupe_key` formats: `suggest_topics:<userId>`, `write_story:<topicId>`, `render_audio:<storyId>:<voiceId>`. Buys one active generation per person, per topic and per story-and-voice with no locks; costs that a second person who wants a topic that is already being written does not get a job of their own (see "Queue top-up", rule 8).
8. **Failure.** The handler returns a 5xx and Cloud Tasks retries with backoff. After the maximum number of attempts the job is marked `failed`. A failed `write_story` leaves no `stories` row. A failed `render_audio` leaves a story without audio in that voice, which is not ready. The queue items that waited for the failed result are removed (section 11, item 13).

**Queue top-up and the daily limit (decided by the owner on 2026-10-30).** One service, `QueueTopUp`, decides what goes into a person's queue and what has to be generated. It may be run again at any time with no harm, which is how the cases below recover. Every run asks for as many items as are missing to bring the queue to three, counting the items that are still being prepared. It runs when the queue has two items or fewer.

1. **Fit.** A topic fits a person if its style is among their styles and its interest is among their interests (the intersection counts; in the shared pool a topic without an interest, made for a typed interest, never matches; the person's own proposed topics may have none), and if the person has not heard the story, does not have the topic in the queue, has not dismissed it, and has not rated its story -1. A topic that any person requested by typing (a `user_topics` row with the reason `requested`) is never offered to anyone else.
2. **Order of sources, each filled before the next, picking at random within one:**
   1. Ready stories (a `story_audio` row exists in the person's voice): added to the queue. Free, no limit is used.
   2. Stories with no audio in the person's voice: added to the queue, and a `render_audio` job is created. Uses one render.
   3. The person's own proposed topics that have no story yet (on the "Темы" tab, not in the queue): added to the queue, `write_story` and then `render_audio` follow. Uses one render.
   4. If that is still not enough, a `suggest_topics` job runs. It adds 10 to 15 topics to the "Темы" tab; the missing number is picked at random from them, added to the queue, and then `write_story` and `render_audio` follow. Uses one topic generation, and one render per story. The other new topics only appear on the tab; nothing writes a story for a topic that is not in the queue.
3. **The limit, per person, in a rolling 24 hours (no time zone and no midnight reset).** At most 5 renders: the renders finished in the window, plus `render_audio` jobs that are pending or running, plus `write_story` jobs that are pending or running (each will need a render). At most 3 `suggest_topics` jobs, counted the same way. So with four renders done, a fifth story being written or voiced leaves no room; with three done and two in progress, none either. A failed job frees its slot; the retries inside one job are not counted, and the vendor-side spending caps (section 11, item 8) cover a job that keeps failing and keeps costing.
4. **Where the limit is enforced.** Checking the count and creating the job rows happen in one transaction that first locks the person's `users` row (`FOR UPDATE`, the same as in onboarding). A `CHECK` constraint cannot count rows in a window; the lock is what stops two simultaneous requests from both seeing "four" and both starting a fifth. A test with concurrent requests proves it. Every path that creates a generation job takes this lock, including the handler of `suggest_topics` when it creates the `write_story` jobs: if fewer slots are left than topics were picked, it starts only as many as fit and the rest wait on the tab.
5. **At the limit.** Ready stories are still added to the queue. Anything that needs generation is refused with a clear message (its Russian copy is not written yet), and the topic stays on the tab.
6. **An explicit add from the "Темы" tab** goes through the same rules: a topic whose story and audio exist costs nothing, one with only the story costs a render, one with neither costs a render for the pair.
7. **Typed topics** (`requested`) go through `write_story` and `render_audio` like any other and use the same limit, but are never reused (SECURITY.md, rule 10).
8. **Two people want the same topic at the same time.** The second hits the active `write_story:<topicId>` key (or `render_audio:<storyId>:<voiceId>`) and gets no job of its own; its queue item stays "preparing" and uses no slot. The item is already in the queue, so the candidate searches never offer it again, and the winner's chained render is in the winner's voice, which may differ. The **stalled-items step** of the top-up heals this. At the start of every run, after the lock and before the `queue_full` return, it finds the person's own queue items whose topic has a story, has no audio in the person's voice, and has no `render_audio:<storyId>:<voiceId>` job row of ANY status from any requester (an active job of someone with the same voice will produce the shared audio; a finished or failed one is not this step's business), and which the person has not heard or rated -1. That is exactly the dedupe loser, which has no job of that key at all. Each gets a `render_audio` job and costs one render slot, taken off before the rest is planned; at the limit the item waits. Stalled items without a story (no write job either) are failure handling, not done here (item 13). A failed `render_audio` is NOT retried by the top-up: the step heals only an item with no render job of its key at all, so a failed render leaves the queue item "preparing". Decided in cycle 3b-1 (item 13): the final failure removes the item for everyone waiting on that result, so a failed item never stays "preparing".
9. **The first person in an empty database** goes through all of source 4, so the first queue appears after about a minute; the app shows a "preparing" state. The pool grows with use.

**How the top-up is built (cycle 3a, 2026-10-30; the database part only).** `QueueTopUpService.run(userId)` in `apps/api/src/app/queue` does the steps above in one transaction behind the `users` row lock. Nothing calls it yet, and no HTTP route, no handler and no provider call exists in this part. Choices the owner approved, where the text above left room:

- **Queue length** is the number of `queue_items` rows of the person, including items still being prepared.
- **Heard** means any `listens` row for the story, finished or skipped; such a topic is not offered again.
- **No suggestion without a render slot.** `suggest_topics` is not started when no render slot is left, because it could not be followed by a write. Ready stories are still queued.
- **New items are appended:** position is the current maximum plus one, in the order ready, rendering, writing.
- **Preferences are required.** A person without `user_preferences` (voice and styles) gets nothing.
- **Custom interests do not affect pool matching.** They matter only to the text of `suggest_topics`.
- **No `user_topics` row for a pool topic.** The top-up queues a pool topic without writing a `user_topics` row. The "Темы" tab shows the fitting pool topics plus the person's own proposed ones (owner, 2026-10-30).
- **A NULL interest is private by construction.** The two pool finders (ready, rendering) require the topic's interest to be one of the person's, so a topic with no interest never reaches another person's queue (SECURITY.md, rule 10). Only the finder of the person's own proposed topics accepts a NULL interest. Costs: the isolation depends on the suggest step setting the interest to NULL for a topic grown from a custom interest (section 11, item 29).
- **`NoopJobQueue`** is bound as the `JobQueue` when `JOB_QUEUE=none` (the default outside production): it dispatches nothing, so a created job row stays `pending` until the sweep or an explicit call picks it up. `env.ts` refuses `none` in production and on Cloud Run. `JOB_QUEUE=local` binds the development queue (section 11, item 7). `JOB_QUEUE=cloud-tasks` is accepted by the environment schema but has no implementation yet: the API refuses to start with it until the deployment cycle.
- **A job that finds an active job with the same key** (rule 8) keeps the queue item and uses no slot; the other planned jobs are not backfilled, the next run does it, and the stalled-items step (rule 8) renders such an item once the winner's audio is in another voice. The jobs of a run are inserted in dedupe-key order, so two runs of different people cannot deadlock on the unique index. After the commit the queue is told about each created job; an enqueue error is swallowed and the row waits for the sweep.
- **For the API cycle (not decided here):** the designs show things the data model does not have: mood filters ("Серьёзно", "Загадочно") and "Избранное". They are deferred ideas, not planned and not in the MVP (section 10); the API cycle builds none of them. (The series in the designs, "Продолжить серию · часть 3", are a designer's mistake and are not planned: see section 10.)

**How jobs run (cycle 3b-1, built 2026-10-30; the handlers are cycle 3b-2).** `POST /api/internal/jobs/run` takes `{ jobId }` only; the payload is always read from the row. The executor (`apps/api/src/app/internal`) claims the job (step 3), parses the payload with the contracts schema, finds the handler of the kind and runs it. Numbers (`queue/queue-policy.ts`): lease 10 minutes (longer than the worst job: LLM 90 s, TTS 180 s, upload); attempts per claim, counted at each claim: `write_story` 3, `render_audio` 2, `suggest_topics` 2; the sweep takes `pending` jobs older than 2 minutes and `running` jobs past the lease, at most 50 per call, oldest first. A retryable error (`LlmProviderError`, `TtsProviderError`, `StorageUploadError`, `GenerationError` with the flag) with attempts left releases the job to `pending`; anything else, or the last attempt, is final: the job becomes `failed`, `last_error` holds a code from a fixed vocabulary (never provider or exception text), and in the same transaction the failure policy runs. **Failure policy (owner, 2026-10-30):** a finally failed job removes the queue item of everyone who was waiting for its result, in the same transaction as the `failed` mark: a failed `write_story` for topic T removes every person's item for T (no story will exist); a failed `render_audio` for story S in voice V removes the item for S's topic of every person whose preferred voice is V (a person with another voice has a render job and key of their own and keeps their item; the requester is not special-cased). A failed `suggest_topics` removes nothing. The candidate finders no longer offer a topic with a `failed` `write_story:<topicId>` job or a story with a `failed` `render_audio:<story>:<voice>` job, so nothing is offered again automatically. No user-intent data is written (rule 4 of AGENTS.md). Outcome to HTTP: `succeeded`, `failed` and `finished` (already done, dropped, or taken over) answer 200 `{ status }`; `retry` and `in_progress` answer 503 with the fixed body `{ statusCode: 503, code: 'job_retry', message: 'Try again later' }`, so the queue delivers again with its backoff. `POST /api/internal/jobs/sweep` (for Cloud Scheduler) answers 200 `{ enqueued }` and hands ids to the `JobQueue`; the claim decides whether a job runs. Not built yet: the Cloud Tasks implementation of `JobQueue`, the Cloud Scheduler job that calls the sweep (and a periodic top-up), and the production deployment. A job whose kind has no registered handler is not claimed and not failed: the executor checks the registry first and answers `retry` (503) leaving the row untouched, so a deployment without handlers (until cycle 3b-2 registers them) can never hide a topic. There is no `no_handler` failure code.

**Prompts (approved by the owner on 2026-10-30 after manual tests, including a story run through the TTS).** Two prompts, in `apps/api/src/app/generation/prompts`: topics (`topics-v1`) and story (`story-v1`). The story version is stored in `stories.prompt_version`; the wording changes only together with a new version string. Decisions behind them:

- **The system part is static and holds no user data; choices, typed interests, the topic and the style travel in the user message inside tags.** The builders remove angle brackets and line breaks from every value, so a value cannot close its tag or fake another entry (SECURITY.md, rule 7). Buys that a hostile custom interest or topic stays data; costs that a `<` inside a legitimate value is lost.
- **The reply format of the topics prompt is not in the text.** The provider call sets it (structured output from a Zod schema in `packages/contracts`: title, style, optional catalogue interest slug; a topic from a typed interest has no interest). That schema does not exist yet.
- **The topics prompt gets the titles of topics already offered to the person, so it does not repeat them.** The model is asked to compare subject and hero, not words. Pass the most recent ones only (about 100 to 150, a cost of one or two thousand tokens).
- **The story prompt asks for 3 000 to 3 500 characters, but the code checks no range** (owner, 2026-10-30). `write_story` takes the model's text up to the TTS limit of 10 000 characters, with a floor of 500 so an empty reply or a short refusal is never voiced and shared with other people. A reply cut off by the token limit is an error. The constants live in `packages/contracts/src/story.ts`; the numbers 3000 and 3500 exist only in the prompt text.
- **Written for the ear:** plain text, numbers and abbreviations in words, "ё" written out, no lists, markdown or stage directions, no direct address to the listener and no ending with a moral.
- **Not solved:** nothing checks the facts in `facts` and `history` stories. The prompt only asks the model to stay general when unsure. The model can still invent a detail.

Delivery to the phone: the app asks the API for its queue, receives short-lived signed URLs for the audio of ready queue items (a `story_audio` row exists in the person's voice), downloads the files, and plays local files. It reports listens (how many seconds were played) back to the API; whether a listen counts as finished or skipped is derived from that and the audio duration.

**The end of the night.**
1. The last story ends.
2. A gentle sound (waves) starts and fades out over about 20 seconds (the length is a setting). It is one bundled audio file, the same for every voice: not generated, not per voice, not stored in Supabase. The waiting screen shows a visual hint of what to do to continue.
3. A touch anywhere on the screen during the fade continues with further queued stories, which are already downloaded. Touches count as "continue" only in this window; during the stories a touch only wakes the player (see below).
4. No touch: the audio fades out completely, stops, and restores whatever the app changed (Do Not Disturb) and releases the screen (see below).

**The screen during a night.** Decided by the owner on 2026-10-29. Replaces the microphone as the way to tell that the person is still awake, because a person can touch a screen that is on.
- While stories play, the player screen stays on (`expo-keep-awake`). After a few seconds without a touch, the interface goes near-black, the quietest state of the player (the number of seconds is a setting). A touch during a story brings the player back; it does not skip or continue anything.
- There is no brightness library at first. Only the interface is darkened; system brightness is not changed (`expo-brightness` is deferred, section 10). An LCD phone is still lit by its backlight when the interface is black, so how dark it really gets is to be judged on real phones.
- **Releasing the screen must not be forgotten.** The keep-awake lock must be released when the fade ends, when the night is stopped, on any error, when the player leaves the screen and when the app goes to the background, and there should be a hard maximum time as a safety net. A screen left on all night drains the battery and lights the bedroom. When the player is built, check on a real phone that the screen times out normally after a night, including after an error.
- If the person locks the phone themselves, the queue keeps playing, the end-of-night sound plays and fades, and the audio stops; there is no way to continue from the lock screen in the first version. Adding one is decided after real use (section 10).
- Not verified: `expo-keep-awake` on iOS in Low Power Mode (its documentation does not cover it), and how the dimmed interface looks on real phones.

**A constraint for anything that happens with the screen off.** This matters less when the screen stays on, but it still applies whenever the person locks the phone. On Android, JavaScript timers (`setTimeout`, `setInterval`) stop firing while the app is in the background, but native player events keep reaching JavaScript (observed in the background-audio spike on one Android 16 phone). Anything that must happen at a given time with the screen off, such as starting the end-of-night sound or the fade, must be driven by native player events, not by timers.

**Quiet phone.** Android: a custom Expo module toggles Do Not Disturb with media allowed, which needs the user to grant notification-policy access once. iOS: there is no public API, so the person sets up a Focus (such as Sleep) once; media playback is not silenced by Focus.

## 8. Authentication

Supabase Auth with email and password, Google and Apple. The mobile app holds only the Supabase URL and publishable key, signs in, and sends the access token to the API. The API verifies the JWT (with `jose`, against Supabase's published keys; confirm the current signing setup in the docs when implementing) and takes the user id from it. Anything about ownership is looked up by that id and never accepted as supplied by the client. App Store review expects an equivalent privacy-preserving sign-in option whenever third-party sign-in such as Google is offered, and Sign in with Apple is the usual way to satisfy it. Check the current App Store guideline before launch rather than assuming either way.

**Implemented in the sign-up and onboarding feature (2026-10-29).** Email and password only; Apple, Google and "Забыли пароль?" are drawn and inert.
- **API.** A global guard (`APP_GUARD`, deny by default) verifies the bearer token with `jose` against the key set at `SUPABASE_URL`, accepting only ES256 and RS256 and requiring the expected issuer and audience. The user id is the `sub` claim and nothing else. An invalid token is 401; an unreachable Auth service is 503 `auth_unavailable`; logs carry only the error class. `@Public()` opts a route out. The `users` row is created lazily, inside the transaction of `PUT /api/me/onboarding`, so there is no trigger and no foreign key into `auth`. `GET /api/me` returns `{ onboardingCompleted, preferences }`; onboarding is complete when a `user_preferences` row exists, so the server is the source of truth and the app never stores that fact. The endpoint is idempotent (repeating it replaces the answers) and locks the user row, and `user_preferences` is written last. Request bodies are `strict` Zod objects (an extra `userId` is a 400) and responses are parsed by their schemas and fail closed (`nestjs-zod`). Shared schemas live in `packages/contracts` (`@sleep-stories/contracts`); the module-boundary lint rule is on and was proven by a forbidden import.
- **Error bodies.** 401, 400, 422 and 503 match `ApiErrorResponseSchema`. Nest's own 404 and 500 and body-parser errors do not (`{statusCode, message}`), so the mobile client tolerates a body without a `code`.
- **Session on the device.** supabase-js stores the session through an encrypted storage (`features/auth/encrypted-storage.ts`): the session JSON is sealed with a fresh AES-256-GCM key (`expo-crypto`), the blob goes to a file and the 32-byte key to `expo-secure-store` (`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`). Buys a session that survives a restart without keeping tokens in plain text, and a SecureStore value limit that does not matter; costs two writes per save and that any unreadable half means "signed out". A 401 from the API signs the user out locally. A pure function (`resolveGate`) decides which route group is shown; the splash screen stays up until the session is restored and the first `/me` has answered. Learned on a phone: in `expo-crypto` 57.0.4, `AESSealedData.fromCombined` takes bytes on Android although its documentation says a base64 string is fine, so the code decodes the string first (a string made every read fail, and the app signed itself out right after sign-up). The pure storage logic is unit-tested with fakes; the Expo wiring can only be checked on a device.
- **Email confirmation is off locally**, so sign-up answers an existing address with "account already exists". That is account enumeration, accepted for this iteration and recorded in SECURITY.md; turning confirmation on in the cloud project closes it.
- **Local testing.** `npx nx test-integration api` runs the `*.int-spec.ts` tests against the local database (25 tests, two users never see each other's data, parallel `PUT`s). `npx nx prisma-seed api` loads the four ElevenLabs voices (maxim, anna, lev, kate) and ten placeholder interests. It fills the provider fields only of rows still marked `none`, so manual configuration is not overwritten, and it never deletes a voice (`user_preferences` references voices with `ON DELETE RESTRICT`). The mobile app takes both catalogues from `GET /api/voices` and `GET /api/interests`; it hardcodes no slugs.

Playing a sound during the listening window would also put the app's own audio into the microphone, and any sound (a TV, a partner, a cough) counts as "awake". Dropping it also removes the per-voice prompt audio and its generation. The spike's detector and scheduler code stays in the branch `spike/background-audio` for reference.

7. **Local development of Cloud Tasks (decided 2026-10-30: the queue posts to the API's own endpoint; built in cycle 3b-1).** Queueing sits behind one interface (`JobQueue`). In the cloud it will create a Cloud Task (not built yet); locally, with `JOB_QUEUE=local`, `LocalJobQueue` starts a `fetch` POST to `http://127.0.0.1:<port>/api/internal/jobs/run` right after the job row is committed and does not wait for the job. The port is read from the running HTTP server at call time. On a 503 it retries after 5 s and 15 s, at most 3 posts in total; any other status or a network error is not retried; every error is swallowed with one fixed log line (no ids, no secret). This is work done after the response, which rule 6 forbids, so it is the single development-only exception. **Credential:** `/internal/*` accepts, in `local` mode only, a per-boot random secret (32 random bytes, held in memory by one `LocalDispatchSecret` instance shared by the queue and the verifier, never in env or logs), compared in constant time. The three modes: `local` accepts only that secret; `cloud-tasks` accepts only a Google OIDC token (RS256, issuer Google, audience `INTERNAL_OIDC_AUDIENCE`, `email` equal to `INTERNAL_OIDC_SERVICE_ACCOUNT` and verified); `none` accepts a Google token when both OIDC variables are set and nothing otherwise. The secret is accepted in no mode but `local`. **Refusals at boot (`env.ts`, proven by `env.spec.ts`):** `local` and `none` are refused on Cloud Run and when `NODE_ENV` is `production`; `cloud-tasks` needs both OIDC variables, and the API refuses to start with it until the Cloud Tasks queue exists. **Routing:** the controller `internal/jobs` (`run`, `sweep`) is marked `@InternalRoute()`, which makes the global user-JWT guard step aside and applies `InternalAuthGuard`; the user guard steps aside only when the route carries both the mark and `InternalAuthGuard` (so a mark without the guard is still authenticated as an ordinary user route, never open), and a test enumerates every route under `internal` and fails when one lacks the mark, and fails for any marked route, anywhere, that lacks the guard. **Not covered locally:** real Cloud Tasks retries and backoff, queue rate and concurrency limits, and double delivery by Cloud Tasks (the claim in section 6, step 3, is tested with parallel calls). They are checked on Cloud Tasks after the first deployment. **At deployment:** `INTERNAL_OIDC_AUDIENCE` must be set explicitly and identically for the Cloud Tasks task and for the Cloud Scheduler job; if no audience is set they default to the full target URL, which differs between `/run` and `/sweep`, and the single exact `aud` check would reject one of them. Three platform settings must also agree with the lease (10 minutes) and the worst job (LLM 90 s, TTS 180 s, upload): (1) the Cloud Run request timeout (default 300 s) above the worst job and at or below the lease, because a timed-out request keeps running with throttled CPU and holds its lease; (2) the Cloud Tasks dispatch deadline (default 10 minutes) about equal to that timeout; (3) the Cloud Tasks retry settings (maximum attempts and maximum retry duration): every 503 answer (`in_progress`, `retry`, and any job while no handler is registered) uses up a Cloud Tasks attempt, and when Cloud Tasks gives up only the Scheduler sweep recovers the job, so the sweep job must exist before launch.

12. **Chaining and dedupe keys for generation jobs (decided 2026-10-30).** `write_story` creates the `render_audio` row in the same transaction that marks the `write_story` job `succeeded` (a requirement, so a slot is never counted twice or zero times; section 6, step 7), the keys are `suggest_topics:<userId>`, `write_story:<topicId>` and `render_audio:<storyId>:<voiceId>` (section 6, step 7), and the queue is filled by the `QueueTopUp` service, not by the jobs (section 6, "Queue top-up and the daily limit"). `generation_jobs` has no foreign key to topics, so `dedupe_key` is still the only link between a queue item and its jobs. The top-up logic and the job rows are done (cycle 3a; section 6, "How the top-up is built"). Notes for cycle 3b: the caller of a top-up must treat Postgres error 40P01 (deadlock) as retryable, although all jobs of a run are inserted in dedupe-key order to avoid it. The executor, the claim, the sweep and the local queue are done (cycle 3b-1; section 6, "How jobs run"). Left for cycle 3b-2: the three handlers (`suggest_topics`, `write_story`, `render_audio`) and the isolation of private topics between the two suggestion calls, and the trigger after onboarding. Left open after that: how often the Scheduler runs the top-up and which request payload (a typed topic, a tab add) creates which job.
13. **Stuck jobs (decided 2026-10-30, cycle 3b-1).** A job holds its dedupe key while it is `pending` or `running`, so a lost one must be found. Decided: the order is insert the row, commit, then enqueue; a `running` job past the 10-minute lease can be claimed again; a sweep (`POST /api/internal/jobs/sweep`, for Cloud Scheduler) re-enqueues `pending` jobs older than 2 minutes and `running` jobs past the lease, at most 50 per call; the claim decides whether they run. A finally failed job removes the queue item of everyone waiting on its result (owner, 2026-10-30: "remove for everyone who was waiting"; the `queue_items` rows are deleted in the transaction that marks the job `failed`; `write_story` by topic for all people, `render_audio` by the story's topic for people with that voice) and its topic is not offered again automatically; attempts are 3 for `write_story`, 2 for `render_audio` and `suggest_topics`. Local mode has no timer and no boot-time sweep on purpose: a local database can hold stale `pending` rows and a sweep would spend real money on them. No index was added for the lookups of the failure exclusions (`dedupe_key` with status `failed`) or for the sweep's status and time filter; that is fine at this scale, and it is to be revisited when `generation_jobs` grows (it is never pruned). Still missing: the Cloud Scheduler job that calls the sweep (deployment cycle). Two known edges: a person who switches their voice to a voice whose render already failed keeps an item that can never heal (the stalled-items step sees the failed row for that key); and while no handlers are registered (before cycle 3b-2) stale jobs answer 503 and stay `pending`, so more than 50 of them would fill every oldest-first sweep batch (no cost, the sweep is manual locally).
14. **Duplicate listens.** `listens` has no client-generated event id or unique key, so a retried offline report of the same listen would create a second row. An idempotency key is undecided.
15. **Deleting an account.** Deleting the Supabase auth user and then the `users` row (the cascade removes the rest) is not wired. App Store review expects in-app account deletion; it is on the pre-launch checklist in SECURITY.md. The cascade does not remove everything a person wrote: text the person typed (custom topic requests) remains in the shared `topics` table, because content has no owner column and its references are `RESTRICT`, and in `generation_jobs.payload`, because `requested_by_user_id` is only set to null. The cascade also removes the person's `user_topics` rows, including the `requested` row that keeps a typed topic out of the pool, so a deleted person's topic would become pool-eligible: deletion must delete or anonymise those topics before the cascade. What to do with that text (anonymise, delete or keep) is to be decided. Since reuse (section 6) it is also never offered to anyone else, so it does not leak while it waits for that decision (SECURITY.md, rule 10).
16. **Graceful shutdown.** `PrismaService.onModuleDestroy` never runs on SIGTERM because `main.ts` does not call `enableShutdownHooks`. Belongs to the Cloud Run deployment task.
17. **Where a person rates a story.** Ratings are in the MVP scope (section 1) but the screen and moment for rating are not decided.
18. **Orphaned audio objects.** `render_audio` uploads the file before the database transaction, so a failure between the upload and the commit leaves an object in storage with no `story_audio` row. The path is deterministic, `stories/<storyId>/<voiceId>.mp3`, and uploaded with upsert (owner decision, 2026-10-30), so a retry overwrites the same object and never duplicates it. What remains is the object with no row after a crash, which is overwritten on retry; a story that is never retried leaves it. Cleaning those up is not decided.
19. **Packaging and caching of the built API.** `generatePackageJson` in `apps/api/webpack.config.js` writes `dist/apps/api/package.json` without `@prisma/client`, although the bundle requires `@prisma/client/runtime/client` and the query-compiler wasm (checked on 2026-10-09 against a fresh build), and `@prisma/adapter-pg` does not depend on `@prisma/client`. A pruned install or the future Docker image would fail at startup. The generated `package.json` also lacks `pg` and `tslib` (the bundle requires `tslib`; checked against `dist/apps/api/package.json` after a build), so a pruned install would resolve `pg` through `@prisma/adapter-pg`'s `^8.16.3` range and the `8.23.1` pin would not reach production. Separately, the cache inputs of the `build` target do not hash `@prisma/client` (the bundle inlines the generated client); it is covered today only because `prisma` is hashed and both are pinned to the same version. Belongs to the Cloud Run deployment task.
20. **Concurrent double delivery of the same Cloud Task (resolved for the executor in cycle 3b-1).** Cloud Tasks delivers at least once. The claim (section 6, step 3) is one conditional `UPDATE` with a lease, so overlapping deliveries of one job cannot both run it, and `markSucceeded` is fenced on the claim's `attempts` value, so a run whose lease was taken over cannot mark success or commit its rows. Proven by integration tests with parallel calls and with a stale run. What remains for cycle 3b-2: `suggest_topics` has no natural unique key, so its handler must write inside the fenced transaction only (the fence makes a stale second run roll back).

28. **Shared stories are not moderated.** With reuse (section 6, "Queue top-up"), one weak or off-tone story reaches everyone whose styles and interests fit it. The only filters are the prompt itself (section 6, "Prompts") and each person's own -1 rating. Nothing checks a story before it is shared, and no rule removes a story that many people rate -1. Decide before launch what to do (a threshold of -1 ratings that hides a story, or a review of the first stories by hand).
29. **Private topics rely on the model marking them.** A topic grown from a person's custom interest is kept out of other people's queues only because its interest is NULL (section 6, "How the top-up is built"), and the suggest step gets that from the model's structured reply, which a model could get wrong. In cycle 3b, the `suggest_topics` handler should keep the isolation structural: a separate LLM call that sees only the person's custom interests, with the interest forced to NULL, and a catalogue call that never sees them. The API cycle must also insert a requested topic and its `requested` `user_topics` row in ONE transaction; between two commits the topic would be visible to the pool.
